## Analysis

### 1. Dependency Structure
This is **inherently sequential** with a recurrence relation: `out[i] = clamp(out[i-1] + a[i], 0, CAP)`. Each iteration depends on the previous result due to the clamping operations. When the reservoir hits empty (0) or full (CAP), information is lost (spills/shortfalls are discarded), making it impossible to reconstruct earlier states from later ones.

However, the algorithm can be parallelized using **prefix-sum with a custom associative operator** if we track not just the level but also the "potential" (unclamped cumulative sum) and apply clamping rules during the combine phase. This requires careful design of a segment-merge operator.

### 2. Arithmetic Intensity
**Very low**. Per iteration:
- Read: 1 value from `a` (~8 bytes)
- Write: 1 value to `out` (~8 bytes)  
- Compute: 1 add, 2 comparisons, 1-2 conditional assignments (~5-10 FLOPs equivalent)

Arithmetic intensity ≈ 5-10 ops / 16 bytes ≈ **0.3-0.6 ops/byte**. This is **memory-bandwidth-bound** at realistic sizes. The sequential version will be limited by memory latency and bandwidth, not computation.

### 3. Communication
For a parallel prefix-sum approach:
- **Distributed (MPI)**: Each process computes local prefix, then needs to exchange boundary "state" (level + potential range) with neighbors in log(P) rounds. Communication is O(log P) rounds with small messages.
- **Shared-memory**: No explicit communication, but requires synchronization barriers between prefix levels.
- **GPU**: Similar to shared-memory but with warp/block-level synchronization.

### 4. Separable Parts
The algorithm has two conceptual phases:
1. **Input generation** (`change_of`): Embarrassingly parallel, compute-bound (modulo operations)
2. **Reservoir simulation**: Sequential recurrence with potential for parallel prefix

## Recommendation

For **N=1,000,000** with such low arithmetic intensity:

- **CUDA**: Poor fit. GPU kernel launch overhead and memory transfer costs dominate. The algorithm is memory-bound and the recurrence requires complex parallel prefix with many synchronization points. Unlikely to beat CPU.

- **MPI**: Poor fit for this size. Communication overhead in parallel prefix (log P rounds) exceeds computation time. Only worthwhile for N >> 10^9 with careful implementation.

- **OpenMP**: Marginal. Parallel prefix with custom operator is possible but complex. For N=10^6, overhead of thread spawning and barriers likely exceeds benefit. Might achieve 2-4× on many cores if implemented perfectly, but not worth the complexity.

- **SERIAL with optimization**: Best choice. The sequential loop is simple, has excellent cache locality, and modern compilers can optimize it well (loop unrolling, branch prediction). The memory-bound nature means parallelization overhead will dominate any gains at this scale.

**Verdict**: Use SERIAL with `-O3` optimization. The algorithm is inherently sequential, memory-bound, and too small to amortize parallelization overhead. A well-optimized serial implementation will be fastest and simplest.
