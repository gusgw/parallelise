# Analysis of π Estimation by Numerical Integration

## 1. Dependency Structure
**Embarrassingly parallel with a reduction.** Each loop iteration computes an independent term `4.0 / (1.0 + x*x) * h` that depends only on the iteration index `i`. The only dependency is the final sum reduction. No iteration depends on any other iteration's result.

## 2. Arithmetic Intensity
**Low arithmetic intensity; memory-bandwidth-bound at scale.**

Per iteration:
- **Computation**: ~6-8 FLOPs (1 add for x, 1 multiply, 1 multiply for x², 1 add for denominator, 1 divide, 1 multiply by h)
- **Memory**: 8 bytes read (if `i` streamed), 8 bytes for partial sum accumulation
- **Ratio**: ~1 FLOP/byte or less

This is a **textbook memory-bound** problem. At N=10M iterations:
- Total work: ~80M FLOPs (trivial, <1ms on modern CPU)
- Memory traffic: minimal (loop counter, accumulator in registers)
- **Actually compute-bound** because the working set fits entirely in registers/L1 cache

The algorithm is so lightweight that:
- **Shared-memory CPU**: Excellent fit; overhead of thread creation must be amortized over enough work
- **Distributed CPU (MPI)**: Overkill for single-node sizes; only justified for N >> 10⁹ or multi-node requirements
- **GPU**: Poor fit due to kernel launch overhead dominating the trivial computation at realistic sizes

## 3. Communication
If distributed across P processes:
- **Initial**: Broadcast parameters (a, b, n) – 24 bytes, once
- **During**: None (no inter-iteration dependencies)
- **Final**: All-reduce to sum P partial results – 8 bytes per process, once

Communication is **negligible** (single reduction at end). The algorithm is embarrassingly parallel.

## 4. Separable Parts
Single homogeneous loop; no separable phases.

---

## Recommendation

**OpenMP** is the clear winner:
- Trivial `#pragma omp parallel for reduction(+:s)` parallelizes perfectly
- Zero communication overhead (shared memory)
- Scales linearly with cores up to memory bandwidth limits (which won't be hit here)
- At N=10M, expect 4-8× speedup on typical 8-core workstation

**Poor fits:**
- **CUDA/GPU**: Kernel launch overhead (~5-20μs) comparable to entire computation time; data transfer would dominate
- **MPI**: Process creation, MPI_Init, and network stack overhead dwarf the computation; only makes sense for distributed requirements or N >> 10⁹

**Also suitable:**
- **SERIAL** with `-O3 -ffast-math`: Compiler auto-vectorization may achieve 2-4× speedup; perfectly acceptable if simplicity is valued
- **MPI**: Only if the production context requires distributed execution for other reasons

**Expected speedup**: Near-linear with core count (7-8× on 8 cores) due to perfect load balance and negligible synchronization overhead.
