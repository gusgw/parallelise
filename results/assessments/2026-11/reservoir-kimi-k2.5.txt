## 1. Dependency Structure

The core computation in `reservoir()` is **inherently sequential**:
- `level[i] = clamp(level[i-1] + a[i], 0, CAP)`
- Each step depends on the previous level (stateful accumulation with saturation)

This is a **sequential scan with non-linear state** (the clamping makes it non-associative). Unlike a prefix sum where you can use parallel scan algorithms, the saturation at boundaries creates a hard dependency chain. You cannot compute `level[1000]` without knowing `level[999]`, because the clamping decision depends on the actual saturated value, not just the raw sum.

The checksum at the end is a **reduction**, but it's trivial compared to the main loop.

## 2. Arithmetic Intensity

Per iteration:
- Memory: read `a[i]` (8 bytes if 64-bit), write `out[i]` (8 bytes) = ~16 bytes touched
- Computation: 1 addition, 2 comparisons, 0-2 assignments, 1-2 branches

This is roughly **10-20 FLOPs per 16 bytes** → ~0.6-1.2 FLOPs/byte. This is **low arithmetic intensity**, likely **memory-bandwidth-bound** for large N, but with a critical caveat: the dependency chain limits parallelism regardless of memory bandwidth.

The loop is also **latency-bound** due to the tight dependency: `level` must be ready before the next iteration starts. Modern CPUs can speculate through branches, but the data dependency remains.

## 3. Communication

If distributed: each process would need the **entire prefix state** from its left neighbor to start. The saturation boundary creates a "wave" that propagates left-to-right. You could attempt domain decomposition with speculative execution and fix-up iterations, but convergence is not guaranteed and would require multiple passes.

| Part | Character | Parallelizable? |

## Recommendations

**Primary: SERIAL with aggressive compiler optimization**

The main loop cannot be effectively parallelized due to the sequential dependency. OpenMP, MPI, and CUDA would all struggle:

- **OpenMP**: `parallel for` impossible (loop-carried dependency). Could use `ordered` or `simd` with reduction, but the dependency prevents vectorization across iterations.
- **CUDA**: Same issue—threads would need to synchronize on every element, achieving no speedup.
- **MPI**: Would require speculative boundary values and iterative fix-ups; the overhead dwarfs any benefit for 1M elements.

**Optimization strategy for serial code:**
- Use `-O3 -march=native`
- Help the compiler: use `restrict`, mark `CAP` as `const`, consider `__builtin_expect` for branch hints
- The pattern `level += change; level = level < 0 ? 0 : (level > CAP ? CAP : level)` may vectorize if rewritten carefully, but saturation breaks simple vectorization

**Tiling/chunking for cache**: The array fits in L3 cache (16 MB for 1M × 8 bytes × 2 arrays), so memory bandwidth isn't the bottleneck—latency is.
