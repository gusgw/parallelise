# Analysis of Dense Matrix Multiply

## 1. Dependency Structure
**Embarrassingly parallel at the outer two loops.** Each element `C[i][j]` is computed independently via a dot product of row `i` of `A` and column `j` of `B`. The innermost `k` loop is a reduction (sum). No iteration of the `i` or `j` loops depends on any other.

## 2. Arithmetic Intensity

For `n×n` matrices:
- **Operations**: `2n³` FLOPs (n² dot products, each requiring n multiplies + n adds)
- **Data movement**: `O(n²)` bytes to read A, B once and write C
- **Arithmetic intensity**: `O(n)` FLOPs/byte — grows linearly with matrix size

At `N=256`:
- ~34M FLOPs
- ~0.5 MB data (assuming double precision)
- **Intensity ≈ 67 FLOPs/byte**

This is **compute-bound** for well-optimized code with cache blocking. However, the naive triple-loop implementation shown has poor cache locality (striding through B column-wise), making it effectively **memory-bandwidth-bound** without optimization.

**Implications:**
- **Shared-memory CPU (OpenMP)**: Excellent fit. Near-linear speedup expected with proper thread count. Cache-aware blocking would help further.
- **GPU (CUDA)**: Excellent fit for larger matrices. At N=256, launch overhead may dominate, but still beneficial. Needs tiling/shared memory for peak performance.
- **Distributed (MPI)**: Overkill for N=256. Communication overhead would dominate. Viable only for N >> 1000.

## 3. Communication

If distributed across processes using domain decomposition:
- **Block distribution**: Partition C into blocks; each process needs corresponding row-blocks of A and column-blocks of B
- **Cannon's or SUMMA algorithm**: Requires `O(√P)` communication rounds for P processes, each exchanging `O(n²/P)` data
- **Frequency**: One-time setup broadcast/scatter, then algorithmic exchanges
- **For N=256**: Communication cost >> computation cost on any realistic network

## 4. Algorithm Parts

This is a **single homogeneous kernel** — no separable phases with different characteristics.

---

## Recommendation

**Primary: OpenMP** — The algorithm is embarrassingly parallel in the outer loops and compute-intensive enough to benefit from threading. Simple `#pragma omp parallel for collapse(2)` on the `i,j` loops yields near-linear speedup on multi-core CPUs with minimal code complexity.

**Also suitable:**
- **CUDA**: For production code or larger matrices (N ≥ 512), GPU implementations (especially with cuBLAS) deliver massive speedup. At N=256, still worthwhile if GPU is available.
- **Serial with optimization**: A well-optimized serial version (loop reordering, blocking, vectorization, or calling BLAS) may outperform naive OpenMP.

**Poor fit:**
- **MPI**: Communication overhead dominates at this problem size. Network latency and bandwidth costs dwarf the ~34M FLOPs. Only justified for N > 2000 or when distributed memory is required.

**Expected speedup:**
- OpenMP: 4-8× on typical 8-core CPU
- CUDA: 10-50× with proper tiling
- MPI: <1× (slowdown) due to overhead
